# AI Security: Evaluation, Observability & Guardrails

## Why does AI security matter?

Until now, our focus has primarily been AI development:

- Building RAG systems.
- Creating AI agents.
- Implementing tool calling.
- Working with LangGraph.
- Building MCP servers.
- Connecting LLMs with external services.

But consider this situation:

You've built a coding agent that can read files, modify code, execute commands, and fix bugs.

Now imagine someone sends it this instruction:

> Delete Windows from this laptop.

Should the agent execute that instruction?

Obviously not.

This illustrates why AI security is necessary.

An AI system should not only perform its intended tasks but should also:

- Produce reliable results.
- Allow developers to understand its internal execution.
- Prevent unwanted or unsafe operations.

AI Security groups these requirements into three pillars.

**Three pillars of AI security**

**1. Evaluation**

Is my AI system working correctly?

**2. Observability**

Why did my AI system produce this result?

**3. Guardrails**

What should my AI system be allowed to do?

---

## Evaluation (Eval)

### What is Eval?

Eval is short for **Evaluation**.

Evaluation is the process of testing an AI system against predefined test cases to understand whether it is performing as expected.

In simple terms:

**Eval tells you whether your AI system is working correctly or not.**

### Example: Coding agent

Suppose you've built a coding agent that fixes bugs in a codebase.

You prepare 15 test cases, each containing a bug that the agent is expected to solve.

After running the evaluation:

| Test result | Outcome |
|---|---|
| 15 bugs solved | 15/15 passed |
| 10 bugs solved | 10/15 passed |
| 5 bugs solved | 5/15 passed |

If the agent solves all 15 bugs, it performs well on this particular test set.

If it solves only 10, you know that something needs improvement.

You can investigate why the remaining five bugs weren't solved.

### Cricket analogy

Imagine India plays against Pakistan.

India wins by 15 runs.

That is the overall evaluation result of the match.

It tells us whether India won or lost, but it doesn't explain every event that happened during the match.

Similarly, Eval gives you an overall picture of AI system performance.

### Evaluation is not limited to correctness

The instructor also mentions cost.

Imagine your coding agent successfully solves one bug, but the execution costs ₹1 lakh.

Technically, it solved the bug, but the system may not be practical.

So, when evaluating an AI system, we may also care about:

- Task success rate.
- Accuracy or quality.
- Execution cost.
- Efficiency.

**Important distinction:** The lecture introduces Eval as an overall performance assessment. It does not specify a single universal metric or formula for all these dimensions.

## Observability

Now suppose Eval tells you that your AI agent failed five out of fifteen test cases.

The next question is:

**Why did it fail?**

This is where observability comes in.

### What is observability?

Observability helps developers understand what happened inside an application during execution.

It allows us to inspect individual operations and identify where problems occurred.

For example, your coding agent might execute the following sequence:

1. Call an LLM.
2. Execute a Python tool.
3. Call another tool.
4. Call the LLM again.
5. Generate the final response.

If the final response is incorrect, which step caused the problem?

- Was the LLM prompt incorrect?
- Did the tool receive incorrect arguments?
- Did the tool return an unexpected result?
- Did the LLM interpret the tool output incorrectly?

Observability helps investigate these questions.

The lecture introduces three important concepts:

1. Logs
2. Spans
3. Traces

---

### Logs, spans, and traces

These three terms are especially important to understand.

#### Logs

A log is an individual recorded event or message generated by an application.

For example:

```text
10:00:00 - LLM call started
10:00:02 - Tool execution started
10:00:03 - Tool execution completed
10:00:05 - LLM call completed
```

Logs help us understand which events happened and when.

The instructor simplifies a log as a single line of information.

For example:

```text
LLM call happened at 10:00.
```

That tells us an event occurred, but it doesn't provide the complete execution details.

#### Spans

A span represents an individual operation or unit of work within an application.

For example:

- One LLM call.
- One database query.
- One Python function execution.
- One external API request.

The instructor describes five important pieces of information that a span can capture:

| Information | Meaning |
|---|---|
| Input | What data entered the operation? |
| Output | What result did it produce? |
| Cost / tokens | How much did it cost, or how many tokens were consumed? |
| Time | How long did the operation take? |
| Error | Did an error occur? |

Consider an LLM call.

```python
response = llm.invoke(prompt)
```

A span could record:

```text
Operation: LLM Call

Input:
"Explain RAG."

Output:
"RAG stands for Retrieval-Augmented Generation..."

Tokens:
Input: 100
Output: 80

Duration:
1.5 seconds

Error:
None
```

For a Python tool:

```python
result = calculate(10, 20)
```

A span could record:

```text
Operation: Calculator

Input:
10, 20

Output:
30

Duration:
0.002 seconds

Error:
None
```

Cost and token usage are especially relevant for LLM operations. A normal Python function generally won't have LLM token costs.

**Key idea:** A span gives us detailed information about one operation.

#### Traces

A trace represents the complete execution journey of a task.

An AI agent typically performs multiple operations to complete a single user request.

For example:

```text
User Request
     |
     v
  LLM Call
     |
     v
  Tool Call
     |
     v
  LLM Call
     |
     v
  Final Response
```

Each individual operation can have its own span.

The complete collection of related spans forms a trace.

**Example: Coding agent execution**

**Trace: Fix login bug**

Span 1

**LLM call**

Input: Bug description · Output: Debugging plan

Tokens: 500 · Duration: 1.2s · Error: None

Span 2

**File-reading tool**

Input: File path · Output: Source code

Duration: 0.1s · Error: None

Span 3

**LLM call**

Input: Source code · Output: Proposed fix

Tokens: 800 · Duration: 2.0s · Error: None

Span 4

**Code execution tool**

Input: Test command · Output: Tests passed

Duration: 0.8s · Error: None

**Trace completed**

All four spans belong to the same task.

#### Difference between log, span, and trace

| Concept | What it represents |
|---|---|
| Log | An individual recorded event |
| Span | One operation, with its execution details |
| Trace | The complete sequence of related operations |

A useful way to remember:

- **Log:** What happened?
- **Span:** What happened inside this operation?
- **Trace:** What happened throughout the entire task?

### Understanding observability through cricket

The instructor uses cricket to explain the relationship between Eval and observability.

Suppose India loses a cricket match.

#### Eval

Eval tells us:

> India lost the match by 15 runs.

This is the overall result.

#### Log

A log records an individual event.

For example:

> A four was scored on this ball.

#### Span

A span describes an individual operation. In the cricket analogy, the instructor compares it to an over.

For example:

> Four sixes were hit in this over.

#### Trace

A trace represents the entire match execution.

It brings together the events and operations across all 20 overs.

| AI engineering | Cricket analogy |
|---|---|
| Eval | Final match result |
| Log | Individual ball event |
| Span | One over |
| Trace | Entire match |

The important distinction:

Eval tells us that the system failed.

Observability helps us investigate where and why it failed.

*Technical note:* In actual observability systems, logs are not necessarily single lines, and traces contain spans arranged according to their parent-child relationships and timing. The cricket analogy is for understanding, not a strict technical definition.

## Guardrails

Now we come to the third pillar: guardrails.

### What are guardrails?

A guardrail is a security measure or rule that restricts an AI system from performing unwanted, unsafe, or unauthorized actions.

The instructor compares guardrails to the steel barriers installed along highways, especially near dangerous edges.

Why are these barriers installed?

To prevent vehicles from going off the road.

Similarly, AI guardrails are designed to prevent an AI system from crossing defined boundaries.

### Example 1: Coding agent

Suppose you've built a coding agent.

Its responsibilities include:

- Reading source code.
- Finding bugs.
- Editing files.
- Running tests.

Now imagine a user asks:

> Delete Windows from this laptop.

Your agent should not blindly execute this request.

A guardrail can restrict dangerous operations.

### Example 2: Image generation

Suppose a user requests disallowed sexual imagery.

The AI application should refuse the request rather than generate the content.

This is an example of a safety policy acting as a guardrail.

### Example 3: Unauthorized hacking

Imagine a user asks Claude to hack a real website.

The system should refuse assistance that would facilitate unauthorized attacks.

The instructor uses this example to illustrate that AI systems need boundaries even when they have the technical capability to perform an action.

### Example 4: Permission before sensitive operations

Imagine a coding agent wants to modify an important file.

Instead of executing the operation immediately, it can request confirmation from the user.

For example:

```text
The agent wants to delete an important file.

Action requires user approval.

Proceed? Yes / No
```

This is another form of protection.

### Guardrails as a set of rules

You can think of guardrails as defining:

- What the system can do.
- What the system cannot do.
- What requires user approval.
- What inputs should be rejected.
- What outputs should be blocked or modified.

### Are guardrails foolproof?

No.

The instructor explicitly explains that guardrails are not perfect.

An LLM can sometimes be manipulated into behaving in ways that violate its intended rules.

For example, a user might try to bypass restrictions by:

- Rephrasing a prohibited request.
- Claiming the request is only for educational purposes.
- Trying different prompts to override the system's instructions.

Better-designed guardrails make such attempts more difficult, but no single prompt or rule guarantees complete security.

**Important engineering distinction:** Guardrails should not rely only on system prompts. Sensitive actions should also be protected through code-level validation, permissions, access controls, and approval mechanisms.

## How do the three pillars work together?

Let's bring everything together using our coding-agent example.

Suppose you build an AI coding agent that fixes bugs in a repository.

| Situation | Pillar | What it does |
|---|---|---|
| Agent solves 8 out of 10 bugs | Evaluation | Measures overall performance |
| You want to know why two bugs failed | Observability | Helps inspect execution and identify the failure |
| Agent is asked to delete an important system file | Guardrails | Restricts or requires approval for dangerous actions |

**Putting them together**

**AI coding agent**

Reads code · Calls tools · Fixes bugs

- **Eval** · Measure performance
- **Observe** · Understand execution
- **Guardrails** · Enforce boundaries

**More reliable and safer AI application**

The three concepts complement each other:

- Evaluation measures whether the system meets expectations.
- Observability helps explain its behavior.
- Guardrails help prevent unacceptable behavior.

One distinction worth remembering: Eval and observability are broader reliability and operational practices, while guardrails directly enforce safety and security constraints. They work together as part of responsible AI engineering.

## Important questions and answers

**What are the three pillars introduced in AI security?**

Evaluation (Eval), Observability, and Guardrails.


**What is AI evaluation?**

Evaluation is the process of testing an AI system against predefined test cases to measure whether it performs as expected.

**What is observability?**

Observability is the ability to understand an application's internal execution by examining events, operations, and the complete execution flow.


**What is the difference between evaluation and observability?**

Evaluation tells us whether the system is performing well. Observability helps us investigate why it produced a particular result or failed.


**What is a log?**

A log is a recorded event or message generated during application execution, often including information about what happened and when.


**What is a span?**

A span represents an individual operation, such as an LLM call or tool execution. It can record input, output, duration, token usage, cost, and errors.


**What is a trace?**

A trace represents the complete execution journey of a task and groups together the related spans involved in completing it.


**What are guardrails?**

Guardrails are safety and security measures that define what an AI system can do, what it must not do, and which actions require additional validation or approval.


**Are guardrails foolproof?**

No. LLMs can be manipulated, so guardrails need multiple layers of protection, including code-level checks, authorization, and human approval for sensitive operations.


**Can observability prevent an unsafe action?**

Observability helps detect and investigate behavior, but it does not itself prevent an action. Preventive controls belong in guardrails and enforcement mechanisms.

**2. Observability**
- Helps understand application execution.
