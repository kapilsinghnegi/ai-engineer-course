# Understanding Your First LLM Call

## What Is a Virtual Environment?

A **virtual environment** is an isolated Python environment created for a specific project.

It allows each project to have its own:

* Python environment
* Package versions
* Dependencies
* Configuration

without interfering with other projects.

---

### Why Virtual Environments Are Needed

Suppose you have two Python projects:

```text
Project A → requires Package X v2.0

Project B → requires Package X v4.0
```

If both projects use the same global Python environment, upgrading Package X for Project B could break Project A.

Without isolation:

```text
Computer
└── Global Python
    └── Package X v4.0
         ↑
         └── Project A may no longer work
```

With virtual environments:

```text
Computer
│
├── Project A
│   └── Virtual Environment
│       └── Package X v2.0
│
└── Project B
    └── Virtual Environment
        └── Package X v4.0
```

Now each project can use the version it needs.

---

### Why this matters in real development

Different projects frequently require different dependency versions.

Therefore:

> **One project → one isolated environment** is a common and useful development practice.

The source explicitly describes virtual environments as a general software-development practice rather than an AI-specific concept. 

---

## What Is an LLM Call?

An **LLM call** is a request sent from an application to a Large Language Model, followed by the model's response.

For example, when you type:

```text
What is Artificial Intelligence?
```

into an AI application, the application sends your input to an LLM and receives a generated response.

The same thing can be done programmatically through an API.

### Basic flow

```text
Your Application
       │
       │ Request
       ▼
  LLM Provider
       │
       │ Model processes request
       ▼
    Response
       │
       ▼
Your Application
```

An LLM API call therefore has two broad sides:

```text
Input → LLM → Output
```

The important question is:

> **What exactly is included in the input and what exactly comes back in the output?**

That is what this lesson focuses on. 

---

## Components Required for an LLM API Call

At a high level, you need:

```text
API Key
   ↓
Client
   ↓
Model
   ↓
Messages
   ↓
API Call
   ↓
Response
```

The four primary pieces to understand are:

1. **API Key**
2. **Client**
3. **Model**
4. **Messages**

---

### API Key

An **API key** is a credential used to authenticate your application with an API provider.

A simple mental model is:

> **API key ≈ password/credential for accessing an API**

Without a valid API key, your application generally cannot make authenticated API requests.

---

### Client

After obtaining an API key, your application creates a **client** to communicate with the provider.

The API key is used when creating the client so the provider knows that your application is authorized to communicate with it. 

---

### Model

The next requirement is choosing the **LLM model** that will process your request.

For example:

```text
Provider
│
├── Model A
├── Model B
├── Model C
└── Model D
```

Your API request must specify the model you want to use.

Conceptually:

```python
model = "exact-model-id"
```

---

### Messages

Finally, you need to specify **what you want the model to process**.

For example:

```text
What is AI?
```

However, an API message isn't simply a string.

It has structure:

```text
Role
+
Content
```

This distinction is extremely important.

---

## Understanding Messages

### Message Structure

A message can conceptually be represented as:

```python
message = {
    "role": "user",
    "content": "What is AI?"
}
```

So:

```text
message
├── role
└── content
```

#### `role`

Tells the model **who/what the message represents**.

#### `content`

Contains the actual text or instruction.

> **Remember:** A message is not just the question. It includes the role + content.

The lesson initially uses the term "prompt" while explaining the idea, but the actual message schema uses `content`. This distinction becomes important during debugging later. 

---

### User Role

The `user` role represents input from the user.

Example:

```python
{
    "role": "user",
    "content": "Who is Virat Kohli?"
}
```

---

### Assistant Role

The `assistant` role represents a response generated by the model.

Example:

```python
{
    "role": "assistant",
    "content": "Virat Kohli is an Indian cricketer."
}
```

---

### System Role

The `system` role is used to provide high-level instructions that guide the model's behavior.

For example:

```python
{
    "role": "system",
    "content": "Answer every question in one concise sentence."
}
```

Now the model has an instruction about **how it should behave**.

#### Example

```text
System:
You are an interview assistant. Give concise answers.

User:
What is polymorphism?

Assistant:
Polymorphism allows objects of different types to be treated through a common interface.
```

The system instruction establishes the desired behavior before the user's actual question.

---

### Role Summary

| Role        | Purpose                       |
| ----------- | ----------------------------- |
| `system`    | Defines behavior/instructions |
| `user`      | User's input                  |
| `assistant` | Model's previous response     |

---

### Conversation Context

One of the most important concepts in the lesson is **conversation context**.

Consider:

```text
User:
Who is Virat Kohli?

Assistant:
Virat Kohli is an Indian cricketer.

User:
What is his age?
```

The second question:

```text
What is his age?
```

only makes sense because of the previous conversation.

Without context:

```text
What is his age?
```

Who is **"his"**?

The model needs the previous messages to understand the reference.

The source uses exactly this example to explain why conversation history and message roles matter. 

---

### Context = Previous Conversation Information

Conceptually:

```text
Message 1
   ↓
Message 2
   ↓
Message 3
   ↓
Current Message
```

The current message can depend on previous messages.

For a chat application, you therefore typically maintain conversation history:

```python
messages = [
    {
        "role": "user",
        "content": "Who is Virat Kohli?"
    },
    {
        "role": "assistant",
        "content": "Virat Kohli is an Indian cricketer."
    },
    {
        "role": "user",
        "content": "What is his age?"
    }
]
```

The model can then interpret `"his"` using the previous messages.

---

### Why Roles Matter for Context

Suppose the conversation contains two pieces of code:

```text
User:
Here is my code: ...

Assistant:
Here is the corrected code: ...
```

Then the user says:

```text
Your code is wrong.
```

The model needs to know which code came from the assistant.

That's why the history is not simply:

```text
"code A"
"code B"
"code is wrong"
```

Instead, it is structured:

```text
user → code A
assistant → code B
user → code B is wrong
```

The role provides important context about **who produced each message**. 

---

## LLM Response

When you make an API request, the API response usually contains much more than just the generated text.

The lesson focuses on two important parts:

```text
choices
usage
```

Conceptually:

```text
Response
│
├── choices
│    └── Generated answer(s)
│
└── usage
     └── Token usage information
```

---

### Choices

`choices` represents the generated output choices.

Why is it called **choices** instead of simply `answer`?

Because an LLM can potentially generate **multiple candidate responses**.

For example:

```text
Prompt:
Suggest a YouTube title.

Possible outputs:

1. How LLMs Work
2. Understanding Your First LLM Call
3. Build Your First AI Application
4. LLM APIs Explained
5. Your First AI API Request
```

The API can represent these as multiple choices.

Conceptually:

```python
choices = [
    answer_1,
    answer_2,
    answer_3
]
```

The lesson explains `choices` as essentially an **array/list of possible answers**. 

#### In the common case

You usually request one response, so there may be only one choice:

```text
choices
└── [0]
```

You can then access the first generated answer.

---

## Usage

`usage` provides information about the **tokens consumed** by the request/response.

Conceptually:

```text
usage
├── input tokens
├── output tokens
└── total tokens
```

The exact fields can vary by API/provider.

The key idea is:

> **Usage tells you how much token-based computation was involved.**

This matters because tokens can affect:

* Cost
* Context-window limits
* Rate limits
* Resource consumption

---

## Understanding Tokens

A **token** is a unit of text produced by a tokenizer.

A common mistake is to think:

> 1 token = 1 word

That is **not always true**.

A tokenizer can split text into pieces depending on the tokenizer and model.

For learning purposes:

```text
Text
  ↓
Tokenizer
  ↓
Tokens
  ↓
LLM
```

For example, a piece of text might be broken into several tokens rather than one token per word.

---

## Why Tokens Matter

### API Cost

Many commercial LLM APIs charge based on token usage.

```text
More input/output
      ↓
More tokens
      ↓
Potentially higher cost
```

### Context Window

Every model has a maximum amount of context it can process.

```text
Conversation
     ↓
Tokens
     ↓
Context Window
```

If the conversation becomes too large, the application may need to reduce, summarize, or otherwise manage the context.

### Usage Tracking

The API can report token usage so you can monitor consumption.

The source specifically connects token usage with API pricing and explains that tokenization will be covered in greater depth later.

## Complete LLM API Flow

The entire lesson can be summarized as:

```text
                API Key
                   │
                   ▼
                Client
                   │
                   ▼
                 Model
                   │
                   ▼
               Messages
                   │
             ┌─────┴─────┐
             │            │
           Role         Content
             │            │
             └─────┬──────┘
                   │
                   ▼
                API Call
                   │
                   ▼
                Response
              ┌────┴────┐
              │         │
           Choices    Usage
              │         │
          Answer(s)   Tokens
```

## Python Implementation

```python
import os
from dotenv import load_dotenv
from groq import Groq

load_dotenv()

api_key = os.getenv("GROQ_API_KEY")

if not api_key:
    raise ValueError("GROQ_API_KEY is missing")

client = Groq(api_key=api_key)

model = "your-model-id"

message = {
    "role": "user",
    "content": "What is an AI?"
}

messages = [message]

response = client.chat.completions.create(
    model=model,
    messages=messages
)

print(response.choices[0].message.content)
```

> **Note:** Model identifiers can change. Use the current model ID supported by the provider rather than blindly copying an old model name.

---

### Important clarification

A larger parameter count does **not automatically guarantee that a model is better for every task**.

Model quality also depends on:

* Architecture
* Training data
* Fine-tuning
* Reasoning capabilities
* Context length
* Inference optimization
* Evaluation performance

So remember:

> **70B describes parameter count, not an absolute quality score.**

## Interview Questions

### Q1. What is an LLM API call?

An LLM API call is a request sent from an application to a language model through an API, along with the required input/context, after which the application receives the model's response.

---

### Q2. What is an API key?

An API key is a credential used to authenticate an application with an API provider.

---

### Q3. Why shouldn't an API key be hard-coded?

Because source code may be exposed through GitHub, logs, screenshots, or other channels. Secrets should be stored securely, commonly through environment variables or a secret-management system.

---

### Q4. What is a client?

A client is the application-side interface used to communicate with an API provider.

---

### Q5. Why do we need to specify a model?

Because an API provider can offer multiple models with different capabilities, costs, context limits, and performance characteristics.

---

### Q6. What is a message?

A structured piece of input/output conversation information containing a role and content.

```python
{
    "role": "user",
    "content": "Hello"
}
```

---

### Q7. What are the three common message roles?

```text
system
user
assistant
```

---

### Q8. Why are roles important?

Roles tell the system what each message represents and who produced it, which is important for interpreting conversation history.

---

### Q9. Why is conversation context important?

Because later messages can depend on earlier messages.

For example:

```text
User: Who is Virat Kohli?
Assistant: Indian cricketer.
User: What is his age?
```

The word `"his"` depends on the previous conversation.

---

### Q10. Why does the API expect a list of messages?

Because an LLM request may contain an entire conversation history, not just one message.

```python
messages = [
    message1,
    message2,
    message3
]
```

---

### Q11. What is `choices`?

`choices` is a collection/list of generated response candidates.

For a typical request with one generated answer:

```python
response.choices[0]
```

gets the first choice.

---

### Q12. How do you extract the generated text?

```python
response.choices[0].message.content
```

---

### Q13. What is `usage`?

`usage` contains information about token consumption associated with the API request and response.

---

### Q14. What is a token?

A token is a unit of text produced by a tokenizer and processed by an LLM.

It is not necessarily equal to one word or a fixed number of characters.

---

### Q15. Why do tokens matter?

They can affect:

* Cost
* Context-window limits
* Usage tracking
* Resource consumption

---

### Q16. Why use a virtual environment?

To isolate dependencies and prevent package/version conflicts between projects.

---

### Q17. What is the difference between `prompt` and `content`?

A prompt is the input/instruction conceptually, while `content` is the field in the message structure containing that input.

```python
{
    "role": "user",
    "content": "Explain AI."
}
```
