# Building a RAG System with Qdrant Vector Database

## Why do we need a vector database?

In the previous lesson, you built a RAG system using embeddings. The knowledge base and its embeddings were held in your Python program, and you calculated cosine similarity to retrieve relevant documents.

That approach works for small datasets, but it introduces three main challenges as the knowledge base grows.

### Search performance

Suppose you have a query vector and one million document vectors. A straightforward retrieval implementation compares the query against every stored vector, calculates similarity scores, and selects the top results.

This is a form of linear or brute-force search.

- With a small dataset, this may be fast enough.
- With a large dataset, scanning every vector for every query can become expensive.
- A vector database provides indexing and search methods designed to make similarity search more efficient.

The exact speed depends on dataset size, hardware, indexing configuration, and query requirements. The timings mentioned in the video are illustrative, not universal benchmarks.

### Persistence

If your vectors exist only in a running Python process, they can disappear when the process ends unless you save them somewhere.

Rebuilding embeddings can take time and computational resources, especially for large datasets.

With Qdrant Cloud, you can store vectors remotely and query them later without rebuilding the entire knowledge base every time your application starts.

### Memory usage

Storing a large collection of vectors in your local application's memory can consume substantial RAM.

For example, if you store one million vectors with 384 dimensions each, using 32-bit floating-point values:

```
1000000 × 384 × 4 = 1536000000 bytes
```

That is approximately 1.536 GB in decimal units for the raw vector values alone. Indexes, metadata, payloads, and other overhead require additional storage.

A remote vector database moves the primary storage and search workload away from your application's local memory.

### Summary

| Challenge          | How Qdrant helps                                                       |
| ------------------ | ---------------------------------------------------------------------- |
| Search performance | Provides vector indexing and similarity-search capabilities            |
| Persistence        | Stores data outside the lifetime of your Python process                |
| Local memory       | Stores the collection remotely when using Qdrant Cloud                 |
| Concurrent access  | Provides database infrastructure for applications and multiple clients |

## What is Qdrant?

Qdrant is a vector database that stores vector embeddings and lets you search for vectors similar to a query vector.

In a RAG application, the embedding model converts text into vectors. Qdrant stores those vectors alongside the original text or other metadata, then retrieves relevant records when a user asks a question.

For this lesson, the architecture is:

`Knowledge base`: `knowledge.txt` => `Sentence Transformer`: Converts each document into a 384-dimensional embedding => `Qdrant collection`: Stores IDs, vectors, and text payloads => `Semantic search`: Retrieves the most similar records for a question => `Groq-hosted LLM`: Uses retrieved text as context to generate an answer

The key change from the previous lesson is that Qdrant now handles vector storage and retrieval, instead of your Python code manually searching through every embedding.

Qdrant is not the embedding model and does not replace the LLM. Each component has a separate job.

## Collections, points, vectors, and payloads

The video compares a vector database to a traditional relational database to make its terminology easier to understand.

| Traditional database concept   | Qdrant concept |
| ------------------------------ | -------------- |
| Table                          | Collection     |
| Row or record                  | Point          |
| Numeric feature representation | Vector         |
| Associated record data         | Payload        |
| Record identifier              | Point ID       |

A Qdrant collection groups points that share a vector configuration.

Each point can contain three important elements:

1\. `ID`: Uniquely identifies the point within the collection. In the lesson's code, IDs start at `1`.

2\. `Vector`: The numerical embedding generated by the model. Here, each vector has 384 dimensions.

3\. `Payload`: The original text associated with the vector, stored here as `{"text": documents[i]}`. Qdrant can return it with search results so the LLM receives readable context.

### Why is the payload important?

Imagine your knowledge base contains this sentence:

> Employees receive 24 days of paid leave per year.

The embedding model converts that sentence into a vector. Qdrant uses the vector for similarity search, but the LLM needs the original sentence to answer the question in natural language.

The payload preserves the text associated with the vector.

Without a retrievable copy of the original text or another way to map results back to source documents, your application would have to reconstruct that relationship separately.

## Understanding the code, part by part

### Part 1 — Connect to Qdrant Cloud

```py
client = QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY)
print("Connected to Qdrant Cloud!")
```

This creates a client for your Qdrant cluster.

### Part 2 — Create a collection

```py
COLLECTION_NAME = "knowledge"
EMBEDDING_SIZE = 384
client.create_collection(
    collection_name=COLLECTION_NAME, 
    vectors_config=VectorParams(
        size=EMBEDDING_SIZE,
        distance=Distance.COSINE
    ),
)
```

The code creates a collection named `knowledge`.

Two settings matter:

- `size=384`: every stored vector must have 384 dimensions.
- `distance=Distance.COSINE`: Qdrant uses cosine distance to rank vector similarity.

The embedding size is determined by the embedding model, not by Qdrant. Since `all-MiniLM-L6-v2` generates 384-dimensional embeddings, the configured size matches the model.

#### Why does the code delete an existing collection?

The original code checks whether the collection exists and deletes it before recreating it:

```py
if client.collection_exists(COLLECTION_NAME):    
    client.delete_collection(COLLECTION_NAME)
```

This makes the example start with an empty collection every time.

Be careful: this permanently removes the existing collection and its data. It is acceptable for a disposable tutorial environment, but you should not use this pattern in production or with important data.

For a real application, create the collection only when it does not exist, or manage collection changes through an explicit migration process.

### Part 3 — Load the knowledge base

```py
with open("knowledge.txt", "r", encoding="utf-8") as f:
    documents = [line.strip() for line in f if line.strip()]
    print(f"Loaded {len(documents)} documents")
```

Suppose `knowledge.txt` contains:

```txt
Employees receive 24 days of paid leave per year.
Employees can work from home on Mondays and Fridays.
The standard notice period is 90 days.
The office is located in Bengaluru.
```

The code converts the file into a Python list:

```py
documents = [
    "Employees receive 24 days of paid leave per year.",
    "Employees can work from home on Mondays and Fridays.",
    "The standard notice period is 90 days.",
    ...
]
```

Each non-empty line becomes one document. In this tutorial, a document is a single line of text, although production RAG systems often use chunks of larger documents.

### Part 4 — Generate embeddings

```py
model = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = model.encode(documents)
print(len(embeddings))
print(len(embeddings[0]))
```

The model transforms each text document into a numerical vector.

If you have six documents, the result has six vectors, each containing 384 numbers.

Conceptually:

Input text: `Employees receive 24 days of paid leave per year.`
↓
Embedding model: `all-MiniLM-L6-v2`
↓
Output vector: 384 numerical dimensions - `[-0.021, 0.034, 0.012, ...]`

The numbers above are illustrative, not actual model output.

### Part 5 — Convert embeddings into Qdrant points

```py
points = []
for i, embedding in enumerate(embeddings):    
    point = PointStruct(        
        id=i + 1,        
        vector=embedding.tolist(),        
        payload={"text": documents[i]}    
    )    
    points.append(point)
```

The index connects the vector and its source document. For example, `embeddings[0]` is paired with `documents[0]`.

### Part 6 — Upload points using `upsert`

```py
client.upsert(    
    collection_name=COLLECTION_NAME,    
    points=points
)
```

`upsert` means insert or update.

- If a point with the same ID does not exist, Qdrant inserts it.
- If a point with the same ID already exists, Qdrant updates it.

This is different from blindly appending duplicate records. However, because the tutorial deletes the whole collection first, the subsequent upload starts from an empty collection.

At this stage, the knowledge base has been embedded and stored remotely.

### Part 7 — Search Qdrant

Your retrieval function is:

```py
def search(query, top_k=3):    
    query_vector = model.encode(query)    
    results = client.query_points(        
        collection_name=COLLECTION_NAME,        
        query=query_vector,        
        limit=top_k,        
        with_payload=True,    
    ).points
    return results
```

This function performs two key operations.

First, embed the query.

For example:

```py
query = "How many days of vacation do I get?"
query_vector = model.encode(query)
```

The query must be embedded using a compatible embedding model so its vectors can be compared with the stored document vectors.

Second, retrieve the most similar points.

- `collection_name`: the collection to search.
- `query`: the query vector.
- `limit=top_k`: the maximum number of results requested.
- `with_payload=True`: asks Qdrant to return the associated payload as well.

The results contain information such as a point's ID, similarity score, vector if requested, and payload.

`top_k=3` means return up to three results. It does not guarantee that all three are relevant.

### Part 8 — Inspect search results

```py
query = "How many days of vacation do I get?"
results = search(query, top_k=2)
for result in results:    
    print(f"Score: {result.score:.3f}")    
    print(result.payload["text"])
```

The query should retrieve the paid-leave sentence near the top of the results.

The score measures how closely the query matches each stored vector under the selected distance configuration. With cosine-based ranking, higher similarity generally indicates a closer match.

A result with a lower score may still be relevant, and the score alone does not prove that a result contains the correct answer.

### Part 9 — Connect to Groq

```py
groq_client = Groq(api_key=GROQ_API_KEY)
```

This creates the client used to call the language model. It is separate from the Qdrant client.

The two clients serve different purposes:

- Qdrant retrieves relevant information.
- Groq provides access to the LLM that generates the answer.

### Part 10 — Ask the LLM using retrieved context

```py
def ask_llm(question, context):    
    prompt = f"""    
        Answer the question using only the information provided below.    
        Context:    {context}    
        Question:    {question}    
        If the answer is not present in the context, answer:    
        "I can't provide the answer to this question based on the information provided."    
    """    
    response = groq_client.chat.completions.create(        
        model="openai/gpt-oss-120b",        
        messages=[            
            {"role": "user", "content": prompt},        
        ],    
    )    
    return response.choices[0].message.content
```

The prompt supplies the model with the user's question and the retrieved text.

This is the generation stage of RAG. The model is instructed to answer from the supplied context and acknowledge when the context is insufficient.

That instruction helps reduce unsupported answers, but it is not a guarantee against hallucinations. Also, the exact model identifier must be available to your Groq account when you run the code.

### Part 11 — Complete the RAG pipeline

The last part of your supplied code has an incomplete assignment:

```py
question = "How many days of vacation do I get?"
```

You must provide an actual question. The remaining steps are to retrieve documents, extract their text, and ask the LLM.

Here is a complete version:

```py
question = "How many days of vacation do I get?"
# 1. Retrieve relevant points from Qdrant
results = search(question, top_k=3)
# 2. Extract the text payloads
context = "\n".join(result.payload["text"] for result in results)
# 3. Generate the answer using the retrieved context
answer = ask_llm(question, context)
print("\nFinal Answer:")
print(answer)
```

The expected answer, assuming the knowledge base contains the corresponding sentence, is that employees receive 24 days of paid leave per year.

## The complete RAG pipeline

Let's connect the concepts into a single mental model.

### Ingestion

Read `knowledge.txt` and split its contents into documents.

### Embedding

Convert every document into a vector using `all-MiniLM-L6-v2`.

### Storage

Upload each vector, ID, and payload to the Qdrant `knowledge` collection.

### Retrieval

Embed the user's query and ask Qdrant for the top matching points.

### Augmentation

Extract the original text from the returned payloads and include it in the LLM prompt.

### Generation

The LLM produces an answer grounded in the supplied context.

The central insight is that you no longer implement the similarity-search loop yourself. Your application delegates vector storage and retrieval to Qdrant, then passes the returned text to the LLM.

## Important implementation notes

These are practical caveats to remember when turning the tutorial into a real project.

1. Do not delete the collection on every run in production. The tutorial's reset pattern destroys stored data.
2. Use the same embedding model for documents and queries. The vector dimensions and embedding space must be compatible.
3. Treat retrieved text as evidence, not guaranteed truth. Retrieval quality affects the final answer.
4. Validate environment variables. Missing API keys or URLs should produce a clear error before database operations begin.
5. Handle an empty search result. If no useful context is found, the application should not blindly generate an answer.
6. Do not assume `top_k` means relevance. It controls the number of results, not a minimum relevance score.
7. Consider document chunking. A one-line-per-document knowledge base is suitable for this exercise, but long documents often need thoughtful chunking and metadata.
8. Verify the API version and model availability. Client method names and supported model identifiers can change over time.

## Important questions

### Q1. What is a vector database?

A vector database stores numerical vectors and supports similarity search. In RAG, it retrieves documents whose embeddings are similar to the embedding of a user's query.

### Q2. Why use Qdrant instead of calculating cosine similarity manually?

A manual implementation may scan every vector. Qdrant offers persistent storage, vector indexing, and database search capabilities that can make retrieval more practical for larger datasets.

### Q3. What is a collection in Qdrant?

A collection groups points that share a compatible vector configuration, such as vector dimensionality and distance metric. It is roughly analogous to a table in a relational database, though the underlying data model differs.

### Q4. What is a point?

A point is a record in a Qdrant collection. In this example, it consists of an ID, a vector, and a payload.

### Q5. What is a payload?

A payload stores data associated with a point, such as the original document text. It allows the application to retrieve readable context after vector search.

### Q6. Why is the embedding dimension set to 384?

The tutorial uses `all-MiniLM-L6-v2`, which produces 384-dimensional embeddings. The collection configuration must match the vector dimension returned by the model.

### Q7. What is the purpose of `Distance.COSINE`?

It configures Qdrant to use cosine-based vector comparison. This allows the database to rank vectors by their angular similarity.

### Q8. What does `upsert()` do?

It inserts a point if the ID is new or updates the existing point if the ID already exists.

### Q9. Why use `with_payload=True`?

It requests the associated payload in the search results. This lets the application retrieve the original text and provide it to the LLM.

### Q10. Does a vector database generate answers?

No. Qdrant retrieves relevant records. The LLM generates the answer using the retrieved context and the user's question.

### Q11. Does retrieving the top three documents guarantee an accurate answer?

No. The results may be irrelevant, incomplete, or insufficient. Retrieval quality, chunking, prompts, and the model's behavior all affect the final answer.

### Q12. What is the difference between embedding, retrieval, and generation?

- Embedding: converts text into numerical vectors.
- Retrieval: finds relevant stored records using the query vector.
- Generation: uses the retrieved context to produce a natural-language answer.
